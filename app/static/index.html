HOW THE PONG DEMO WORKS

Internet → GCP L4 Load Balancer (ingress-nginx-controller Service, external IP) → NGINX Ingress Controller → /pong → pong-app Service → Pong Pods.

During Demo Mode Kubernetes changes the Deployment Pod-template annotation every 3 minutes. That creates a real rolling redeployment. A new Pod is started and must pass its readiness probe before the old Pod is terminated. With maxUnavailable: 0 and maxSurge: 1, the application remains available while Pods are replaced.

The terminal never executes arbitrary shell commands. It accepts only an explicit read-only Kubernetes command whitelist. Write operations are separate API actions and require the appropriate application role.

ARCHITECTUREend-to-end flow

This tab documents the GCP clone of the original Azure Kubernetes Service (AKS) lab: the same application, redeployed onto Google Kubernetes Engine (GKE) on branch gcp-exact-clone, reachable over a plain HTTP public IP with no DNS, TLS or CDN in front of it. Everything below describes what is actually running in project migration-lab-gcp-clone, not the Azure original.

Developer │ git push (gcp-exact-clone) ▼ GitHub (repository: azure-migration-lab, branch: gcp-exact-clone) │ triggers .github/workflows/deploy-gcp.yml ▼ GitHub Actions (google-github-actions/auth, secrets.GCP_CREDENTIALS) │ docker build ./app → docker push ▼ Artifact Registry (europe-west1-docker.pkg.dev/migration-lab-gcp-clone/migration-lab) │ gcloud container clusters get-credentials → helm upgrade --install migration-app-prod ▼ Helm (release: migration-app-prod, namespace: prod, -f values.yaml -f values-prod.yaml -f values-gcp.yaml) ▼ GKE (gke-migration-lab, europe-west1-b) ├── Operations Console (this app - FastAPI, Deployment migration-app-prod) ├── Pong application (Deployment pong-app, rolling-restart demo target) └── PostgreSQL (StatefulSet migration-postgresql)

Underneath this sits Terraform (terraform-gcp/), which provisions the GCP infrastructure the pipeline above depends on: the VPC/subnet, the GKE cluster, Artifact Registry and a Secret Manager secret holding the Postgres password. Unlike the Azure original, this Terraform config keeps local state (no remote backend) — a deliberate simplification for a single-operator, throwaway clone.

Terraform (terraform-gcp/*.tf) ▼ GCP Project (migration-lab-gcp-clone) → VPC / Subnet → GKE + Artifact Registry + Secret Manager ▼ (the platform the CI/CD flow above deploys onto)

What can go wrong: a red step in the GitHub Actions run means the build/push/deploy stage itself failed — read that job's log. A green pipeline run with a broken app means the problem moved into Kubernetes (see Troubleshooting). A real incident hit during this clone's setup: a terraform apply crashed mid-run, leaving the GKE cluster created in GCP but missing from Terraform's own state — recovered with terraform import, not a fresh apply (which would have failed on a name collision).

GCPproject → GKE → Artifact Registry → Secret Manager

Project - migration-lab-gcp-clone

GCP's equivalent of the Azure Resource Group: the billing/IAM boundary everything else lives inside. Deleting it (gcloud projects delete) deletes everything inside it — the single biggest blast-radius action for this clone.

VPC & Subnet - vpc-migration-lab / snet-gke

GKE nodes get private IPs from snet-gke (10.20.1.0/24) inside a custom-mode VPC vpc-migration-lab, with two secondary ranges for GKE's VPC-native networking: pods (10.21.0.0/16) and services (10.22.0.0/20). Unlike Azure, a non-default GCP VPC has no pre-created "allow internal" rule, so terraform-gcp/main.tf declares one explicitly (allow-internal-migration-lab) plus a second rule letting Google's own health-check ranges reach the ingress Service (allow-gclb-health-checks).

GKE - gke-migration-lab

Defined in terraform-gcp/main.tf as google_container_cluster.main with remove_default_node_pool = true plus a separate, explicitly-sized google_container_node_pool.system (one e2-medium node — the closest match to Azure's Standard_B2s_v2), in zone europe-west1-b. Workload Identity is enabled on the cluster but is not actually wired to any Pod here — this clone has no GCP API calls to make from inside a Pod, so there was nothing for it to authenticate.

Artifact Registry - migration-lab

The direct equivalent of ACR. Both application images (migration-app, pong-app) live at europe-west1-docker.pkg.dev/migration-lab-gcp-clone/migration-lab. The GKE node pool's own default compute service account is granted roles/artifactregistry.reader (google_project_iam_member.node_pull) so nodes can pull images with no stored registry credential — the same no-password design as AKS's AcrPull role assignment.

Secret Manager - postgres-password

Holds the PostgreSQL password, generated once by Terraform's random_password resource — this clone's equivalent of Key Vault. The important difference from Azure: nothing here auto-syncs it into the cluster. There is no Secret Manager CSI mount and no Workload Identity chain — a human runs terraform output -raw postgres_password and passes it into helm upgrade --set-file at deploy time, which renders it into a plain Kubernetes Secret. If the Secret Manager value were ever rotated, someone would have to manually re-run that Helm command; nothing would pick up the change on its own.

Load Balancer & External IP

Not in Terraform at all — same pattern as Azure. The NGINX Ingress Controller's LoadBalancer Service made GCP auto-provision an external IP and forwarding rule. Installing that controller needed permission this clone's CI identity doesn't normally have (see Security) — its own ClusterRole/ClusterRoleBinding require RBAC-management rights that github-actions-deploy's baseline role deliberately excludes.

TERRAFORMproviders · main · variables · outputs

Four files in terraform-gcp/. providers.tf pins the google provider. variables.tf declares project_id/region/zone. main.tf declares the VPC, subnet, both firewall rules, the GKE cluster and node pool, Artifact Registry, the Secret Manager secret, and the github-actions-deploy service account with its two IAM role bindings. outputs.tf exposes the generated Postgres password for the manual deploy step to read.

Local state, not remote — a deliberate difference from Azure

The Azure project uses a remote Storage Account backend so multiple operators can't corrupt shared state. This GCP clone is a single-operator, short-lived experiment, so terraform.tfstate is a plain local file — there is no locking, and no second person should ever run apply against this same checkout at the same time.

What's actually in state today

terraform state list shows 14 objects: the VPC, subnet, both firewall rules, the GKE cluster, the node pool, Artifact Registry, the Secret Manager secret and its version, the random_password, the CI service account and its two role bindings, and the node-pull role binding. Nothing about ingress-nginx, its RBAC objects, or the Ingress external IP is in Terraform — installed imperatively with helm/kubectl, exactly like the Azure original.

What actually went wrong here, and how it was diagnosed

During setup, a terraform apply was killed mid-run. It had already created the GKE cluster in GCP, but crashed before writing that to state — leaving state and reality out of sync, with a stale lock file left behind besides. Diagnosis: gcloud container clusters list showed the cluster running; terraform state list didn't mention it. Fix: delete the stale lock (no process was still holding it), terraform import google_container_cluster.main the orphaned cluster, then let a normal plan/apply create the one resource that genuinely was still missing (the node pool) — never a blind re-apply, which would have tried to recreate the cluster and failed on a name collision.

DOCKERapp/Dockerfile · pong/Dockerfile

app/Dockerfile - the Operations Console image

FROM python:3.12-slim, installs requirements.txt, then copies only config.py db.py k8s_ops.py main.py and static/ — not the whole build context. Creates and switches to a non-root user (useradd -u 10001, USER 10001) before any application code runs, then starts uvicorn main:app on port 8000. app/.dockerignore excludes __pycache__/ and *.pyc from the build context.

pong/Dockerfile - the demo target image

A much simpler, unrelated image: FROM nginx:1.27-alpine, copies a static index.html and an nginx.conf that adds a plain-text /health endpoint on port 8080. Deliberately "dumb" — its only job is to be something that can be rolling-restarted and scaled repeatedly with no real backend dependency.

Why two separate images

The console and the demo target are deployed, scaled and restarted independently (two Deployments, two Services, two Ingress paths). One shared image would couple two unrelated failure domains for no reason.

What can go wrong

ImagePullBackOff usually means the tag CI pushed doesn't match the tag Helm was told to deploy, or (on this GCP clone) the node service account's artifactregistry.reader role is missing. A build failure shows directly in the GitHub Actions "Build Docker image" step log.

KUBERNETES17 objects actually in use

Pod

The smallest deployable unit. Every running piece of this project — console, Pong, PostgreSQL — is ultimately one or more Pods. Nothing here creates a Pod directly; a Deployment or StatefulSet does.

Deployment

Manages a set of identical, stateless Pods (migration-app-prod, pong-app): desired replica count, Pod template, rollout strategy. Scale and restart in this console both work by patching the Deployment, never a Pod directly.

ReplicaSet

The object a Deployment creates to hold one Pod template's replicas. Every rolling restart creates a new ReplicaSet and scales the old one to zero — that is what "rolling update" means at the API level.

Service

A stable virtual IP/DNS name in front of a changing set of Pods. migration-app-prod, pong-app and migration-postgresql are all ClusterIP. The app reaches Postgres by the Service's DNS name, never a Pod IP.

Ingress

Routes external HTTP traffic by host/path via the NGINX Ingress Controller. The console's Ingress serves /; Pong's serves /pong(/|$)(.*) with a rewrite annotation stripping the prefix before it reaches nginx.

Namespace

A logical partition inside one cluster. This clone uses only prod — unlike the Azure original's dev/test/prod split, this throwaway clone was never meant to carry lighter environments. RBAC Roles are namespace-scoped, so a Role bound in prod has zero effect elsewhere.

ServiceAccount

The identity a Pod uses against the Kubernetes API. Console Pods run as a plain migration-app-prod ServiceAccount (serviceAccount.create: true, no annotations) — no GKE Workload Identity binding, because this clone makes no GCP API calls from inside a Pod that would need one. Every RBAC binding in this project targets this one ServiceAccount.

Secret

Two matter here: migration-postgresql-secret (a plain Secret, rendered by the chart's own template with the Postgres password passed in via helm --set-file at deploy time — see GCP/Security) and migration-ops-secret (LOGIN_PASSWORD/JWT_SECRET, generated once and created directly with kubectl, not by any Helm template).

StatefulSet

Like a Deployment, but for workloads needing stable identity and storage — only migration-postgresql. Its Pod name is always migration-postgresql-0, with its own PersistentVolumeClaim that survives Pod restarts.

PVC / PV

The StatefulSet's volumeClaimTemplates requests a PVC (size from postgresql.storage, 5Gi here, ReadWriteOnce). GKE's CSI storage driver provisions a matching PersistentVolume (a GCP Persistent Disk) automatically — the direct equivalent of Azure's managed-disk-backed PV — so Postgres data survives a Pod reschedule onto a different node.

readinessProbe

Tells Kubernetes when a Pod may receive traffic. The console's probe hits /readyz, which returns 503 until db.is_up() is true — a Pod that can't reach PostgreSQL is pulled out of the Service's Endpoints instead of serving broken requests.

livenessProbe

Tells Kubernetes when to kill and restart a Pod. The console's /healthz is deliberately DB-independent, so a temporary Postgres blip marks the Pod not-ready instead of restarting it in a loop.

Rolling update

Pong's Deployment explicitly sets maxUnavailable: 0, maxSurge: 1: a new Pod must pass readiness before an old one terminates, so replica count never drops during a redeploy. Demo Mode and the ROLLING RESTART button both exercise exactly this.

Scaling

The +/− REPLICA buttons call PATCH on the Deployment's /scale subresource (k8s_ops.scale()), bounded by MAX_REPLICAS (5 in prod). The ReplicaSet controller then creates or deletes Pods to match.

Rollout / restart

A restart without a new image patches the Pod template's annotations (kubectl.kubernetes.io/restartedAt) so the template hash changes and a new ReplicaSet is created even with an identical image tag — k8s_ops.restart(), the same mechanism as kubectl rollout restart.

Kubernetes API

Every console action — read, scale, restart, kill, the terminal — goes through the official kubernetes Python client, authenticated as migration-app-sa. No kubectl binary and no shell exist inside the app container.

HELMchart · values · releases

Chart / Chart.yaml

helm/migration-app and helm/pong-app are two independent charts. Each Chart.yaml declares apiVersion: v2, a chart version (currently 0.1.0 for both) and an appVersion — metadata only, it does not drive the deployed image tag.

values.yaml vs values-prod / values-gcp

values.yaml holds chart defaults, kept in sync with the current FastAPI app: containerPort: 8000, liveness path /healthz, readiness path /readyz — so a bare helm install with no environment file already produces a Pod that can become Ready. values-prod.yaml is the Azure production overlay (Key Vault, ingress, operations-console settings). This GCP clone adds a third layer on top, values-gcp.yaml, applied last (-f values.yaml -f values-prod.yaml -f values-gcp.yaml) so it wins on every key it touches: it disables Key Vault, points the image at Artifact Registry, and — since ingress-nginx now runs here too — re-enables ingress with a host-less catch-all rule instead of Azure's ops.peterhudcovic.tech hostname.

templates/

Deployment, Service, Ingress, ServiceAccount, HPA, the Postgres StatefulSet/Service/Secret, the SecretProviderClass (skipped when keyVault.enabled: false, as it is here), and the RBAC Role/ClusterRole. _helpers.tpl centralizes name/label generation for consistent app.kubernetes.io/* labels across every object.

Release, helm upgrade --install, --set-file, revisions, rollback

A release is one named, tracked deployment of a chart into a namespace. This clone has exactly one: migration-app-prod in namespace prod on the GKE cluster — no dev/test releases here. helm upgrade --install creates the release if missing or upgrades it if present — idempotent, which is why CI can call it on every push. --set-file (rather than Azure's Key-Vault-fed Secret) is how the Postgres password reaches this release: read from terraform output -raw postgres_password into a local file, passed at deploy time, never committed. Every upgrade creates a numbered revision; helm rollback <release> <revision> reverts to a prior revision's rendered manifests.

What can go wrong

The Azure original's own helm history once showed a field-ownership conflict on .spec.replicas from a raw kubectl scale racing a Helm apply — the general fix is always the same: re-run helm upgrade once the conflicting change has settled, or helm rollback to the last good revision. This clone hit a different failure during its own setup: helm upgrade --install ingress-nginx failed outright with a 403 (cannot delete resource "clusterroles") once its CI identity's temporary elevated role had already been revoked — resolved by patching the running Deployment's resource requests directly with kubectl patch instead of another full helm upgrade, since that particular fix needed no RBAC changes at all.

CI/CDGitHub Actions

GitHub Actions - deploy-gcp.yml

git push (gcp-exact-clone, paths: app/**, pong/**, helm/**, deploy-gcp.yml) ▼ GitHub Actions runner ▼ google-github-actions/auth (JSON key, secrets.GCP_CREDENTIALS) ▼ docker build ./app, ./pong → docker push (tag = github.sha) ▼ google-github-actions/get-gke-credentials (gke-migration-lab / europe-west1-b) ▼ helm upgrade --install migration-app-prod ./helm/migration-app --namespace prod -f values.yaml -f values-prod.yaml -f values-gcp.yaml --set image.tag=<github.sha> ▼ rolling deployment (maxUnavailable:0 / maxSurge:1)

Every image tag is the exact Git commit SHA that triggered the build — same discipline as the Azure original, no latest tag anywhere in this flow. One deliberate simplification versus Azure: authentication uses a long-lived JSON service-account key stored as a GitHub secret, not Workload Identity Federation — simpler to set up for a short-lived clone, at the cost of a credential that must be manually revoked when the clone is torn down (see Security).

No Jenkins pipeline for this clone

The Azure original also runs a parallel Jenkins pipeline deploying the same release. This GCP clone was never wired into Jenkins — GitHub Actions is the only deployment path here.

What can go wrong

A red step in the Actions log names the exact failed stage (auth, build, push, Helm). A green workflow with a broken app means the problem moved into Kubernetes — the job's job is done the moment helm upgrade exits 0, it does not wait for the rollout to actually finish.

POSTGRESQLStatefulSet · migration scripts

Where it runs

migration-postgresql is a single-replica StatefulSet running postgres:16, data directory (PGDATA) on a PersistentVolumeClaim so data survives Pod restarts and rescheduling.

Connection flow

Operations Console (main.py) ▼ asyncpg.create_pool(dsn) [app/db.py] ▼ dsn built from DB_HOST/PORT/USER/PASSWORD/NAME [app/config.py] ▼ Service "migration-postgresql" (ClusterIP, port 5432) ▼ StatefulSet Pod "migration-postgresql-0"

The app connects to the Service's cluster-internal DNS name, never a Pod IP — a Postgres Pod restart is transparent to the app once the Service's endpoint updates.

Migration tooling

migration/backup-postgres.sh runs pg_dump -Fc (custom format) against a source database; migration/restore-postgres.sh runs pg_restore --clean --if-exists against the target. migration/README.md documents the cutover: dump → restore → validate → cut writes over → final dump/restore → switch the app's connection → validate again → keep the source around for rollback.

How migration success was validated

docs/rollback.md checks /healthz (liveness) and /readyz (fails with 503 until db.is_up() is true, 200 once PostgreSQL is reachable) after cutover — the same two endpoints the Kubernetes probes themselves use, plus the dashboard's own POSTGRESQL status card for a human-readable view. Keeping a runbook's endpoint names in sync with whatever the application actually exposes is what makes it safe to follow literally during a real rollback, instead of chasing a route that no longer exists.

What can go wrong

See "PostgreSQL connection failure" in Troubleshooting — the console degrades gracefully rather than crashing, because every DB call in db.py checks if not _pool first.

SECURITYRBAC · time-boxed IAM · no-shell terminal

How the Postgres password reaches this cluster (no Workload Identity)

Terraform (random_password.postgres) ▼ stored as the canonical value Secret Manager (postgres-password) ▼ terraform output -raw postgres_password [manual step] ▼ helm upgrade --set-file postgresql.password=... Kubernetes Secret (migration-postgresql-secret) ▼ envFrom / secretKeyRef Pod (migration-app-prod / migration-postgresql)

This is the one place this clone is deliberately less automated than Azure: there is no CSI driver, no Workload Identity, no OIDC federation — a human bridges Secret Manager to the cluster by hand at deploy time. The trade-off is explicit: simpler to set up for a short-lived clone, but a Secret Manager password rotation would silently not reach the cluster until someone re-runs that Helm command.

Time-boxed IAM instead of a standing elevated role

The CI identity github-actions-deploy normally holds only artifactregistry.writer and container.developer — deliberately not container.admin, since that role's RBAC-management rights would let a compromised CI credential grant itself arbitrary cluster permissions. Installing ingress-nginx needed a one-time container.admin grant; each time, it was added immediately before the one helm command that needed it and removed immediately after, verified by confirming the identity's own getIamPolicy call is rejected again.

A real operational cost of this trade-off: because operations.enabled: true makes this chart's RBAC templates (Role/RoleBinding/ClusterRole/ClusterRoleBinding) a standing part of every release, every future helm upgrade of migration-app-prod — not just the first install — needs Helm to reconcile those objects, which needs the same elevated role again. That includes the automated deploy-gcp.yml pipeline: as configured today, a plain CI push would fail on this exact permission error unless a human grants container.admin first. This clone accepts that friction deliberately rather than giving CI a standing elevated role; a less manual fix (splitting the RBAC objects out of the Helm-tracked release, or accepting the standing risk) was left undone.

RBAC: Role vs ClusterRole

A Role (migration-app-prod-operations) grants permissions only inside the namespace it is created in (prod) — get/list/watch/delete on pods, get/list/watch on services/events, get/list/watch/patch on deployments, get/patch/update on deployments/scale, read on ingresses. A ClusterRole (migration-app-prod-node-reader) grants permissions cluster-wide, needed because Nodes aren't namespaced — narrowed to get/list/watch on nodes only. Neither uses a wildcard verb or resource. Both bind to the single console ServiceAccount, and — unlike Azure — that ServiceAccount carries no cloud-IAM identity at all, only these two Kubernetes-native bindings.

Why the namespace scope matters

Because the Role is bound only in prod — the only namespace this clone has — the console's ServiceAccount has zero permissions anywhere else, including kube-system; the API server itself would reject a request there with 403, regardless of what the terminal's whitelist allows.

Why the terminal never runs a shell

k8s_ops.parse_readonly_command() uses shlex.split() only to tokenize typed text for comparison against a fixed set of allowed token sequences — every match dispatches to a specific Python function calling the Kubernetes client library directly. There is no subprocess, no os.system, no shell=True, no eval/exec anywhere in the codebase. An unrecognized command is rejected with an error, never passed to anything that could execute it.

guest / user / admin

Enforced server-side with a FastAPI dependency (require(*roles)) reading the role claim from the signed JWT — never trusted from the request body. guest reaches only read-only endpoints; DELETE /api/pods/{name} requires admin; scale/restart/Demo Mode require user or admin. Registration always assigns the hardcoded role "user" — there is no path for a self-registered account to become admin.

Why passwords aren't in the Git repository

LOGIN_PASSWORD and JWT_SECRET live only in a Kubernetes Secret (migration-ops-secret) created directly with kubectl, never templated by Helm with a literal value. The PostgreSQL password never touches the repo or CI logs — it flows from Terraform's own output straight into a local file (git-ignored) and then a Secret. The CI service-account key used by deploy-gcp.yml is also kept out of the repo (terraform-gcp/.gitignore) and is meant to be deleted along with the rest of this clone (see cleanup).

TROUBLESHOOTINGpractical diagnostic flow
kubectl get pods ▼ Running? Pending? CrashLoopBackOff? kubectl describe pod <name> ▼ Events section — usually names the actual cause kubectl logs <name> ▼ Deployment / ReplicaSet ▼ desired vs ready vs available Service / Endpoints ▼ does the Service see any Pod at all? Ingress ▼ does it point at the right Service/port? Application ▼ app logs, /healthz, /readyz PostgreSQL

The same order used in docs/troubleshooting.md — start at the Pod, work outward only once the Pod itself looks healthy.

CrashLoopBackOff

kubectl logs <pod> --previous to see why the last attempt crashed. In this project the most likely cause is k8s_ops.init() failing on startup with no in-cluster or kubeconfig credentials reachable — confirmed directly by running the console container outside the cluster. Inside GKE this should not happen since the ServiceAccount token is auto-mounted.

ImagePullBackOff

kubectl describe pod Events show either "not found" (Helm was given a tag never pushed to Artifact Registry) or a pull authorization error (the node service account's artifactregistry.reader role is missing).

readinessProbe failure

Pod is Running but 0/1 Ready and gets no traffic. For the console this means /readyz is 503 — check whether migration-postgresql is reachable. For Pong it means nginx isn't answering on 8080 yet. On this clone's single, CPU-tight e2-medium node, a Pod stuck Pending rather than Running is usually FailedScheduling: Insufficient cpu, not a readiness problem at all — check kubectl describe node's Allocated Resources first.

livenessProbe failure

Pod restarts repeatedly after briefly being Ready. Since the console's liveness check (/healthz) is deliberately DB-independent, a liveness failure here points at something more serious than a database blip.

Service without Endpoints

kubectl get endpoints <service> empty means the Service's selector matches no Ready Pod — check the Pod's labels against the selector, and that the Pod is passing readinessProbe (a not-Ready Pod is excluded from Endpoints even if it matches).

Ingress not working / 502

A 502 almost always means the Ingress points at a Service with no healthy Endpoints — check the backend Service first. For pong-app, a wrong rewrite/regex sends nginx a path it doesn't recognize, which shows as a 404 from Pong's own nginx rather than a 502. A 403 while installing the ingress controller itself (not routing through it) means the CI identity's temporary container.admin grant was missing or already revoked — see Security.

Postgres Secret not loading

migration-postgresql-secret never appears, or has the wrong password. Unlike Azure's CSI-driven sync, nothing here re-populates it automatically — check that helm upgrade --set-file postgresql.password=... was actually run with the current value from terraform output -raw postgres_password.

PostgreSQL connection failure

The console does not crash — db.connect() catches the exception, logs a connection-failed message, and every DB call short-circuits on if not _pool. Visible symptom: a degraded but running console (no history, no registered-user login, Demo Mode/registration return 503). Check kubectl logs migration-postgresql-0 and the Secret the app reads its password from.

Helm deployment failure

helm history <release> -n <namespace> shows past attempts. This clone hit one real failure of a different kind: a helm upgrade pre-upgrade hook tried to delete/recreate ingress-nginx's ClusterRole after its temporary elevated IAM grant had already been revoked, and was correctly rejected with a 403. The fix there was to make the specific change needed (a resource-request patch) directly against the running Deployment instead of another full helm upgrade.

Terraform apply failure

Most likely here: managing a resource that already exists but isn't in state yet — Terraform tries to create a duplicate and GCP rejects it on a name collision. This is exactly what happened here after a crashed apply left the GKE cluster orphaned from state. Fix with terraform import, then plan to confirm no unwanted changes, never a forced apply.

RBAC permission denied

A 403 from the Kubernetes API means the request went outside what migration-app-prod-operations or migration-app-prod-node-reader actually grant — most commonly a resource type not listed in either rule set. A 403 from the GCP API instead (e.g. getIamPolicy) means whatever identity is active only holds the baseline container.developer role, not the time-boxed container.admin grant — expected outside the narrow window that grant is active.

KNOWLEDGE CHECK16 questions
What happens after a git push?
On this clone, if the push touches app/**, pong/**, helm/** or the workflow file itself and lands on gcp-exact-clone, deploy-gcp.yml runs: authenticate to GCP via a service-account key, build both images tagged with the commit SHA, push to Artifact Registry, fetch GKE credentials, then helm upgrade --install migration-app-prod with -f values.yaml -f values-prod.yaml -f values-gcp.yaml and --namespace prod. A push outside those paths does not trigger it at all.
Why is Helm used?
The same chart needs to produce different environments (Azure's dev/test/prod, and now this GCP clone) with different ports, probes, replica counts and feature flags — Helm's values-file layering does that without duplicating the Kubernetes YAML for each one, and it gives every deploy a tracked, numbered revision that can be rolled back. This clone adds a third layered file, values-gcp.yaml, on top of the existing two rather than forking the whole chart.
How does Helm rollback work?
helm rollback <release> <revision> re-applies the exact rendered manifests from that earlier revision. It does not rebuild anything — a purely Kubernetes-object-level revert, so the image referenced by that old revision must still exist in the registry (Artifact Registry here) for the rollback to work.
Deployment vs StatefulSet?
A Deployment (migration-app-prod, pong-app) manages interchangeable, stateless Pods with random name suffixes. A StatefulSet (migration-postgresql) gives each Pod a stable, predictable name and its own dedicated PVC that follows that specific Pod — required because a database can't be "any interchangeable replica."
Role vs ClusterRole?
A Role's permissions apply only inside the namespace it's created in; a ClusterRole's apply cluster-wide, needed for cluster-scoped resources like Nodes. This project uses a namespace-scoped Role for pods/services/deployments/ingresses in prod, and a ClusterRole only for the one thing that must be cluster-wide: reading Nodes. Kubernetes RBAC is cluster-native either way — it has nothing to do with the cloud provider's own IAM, which is why this same Role/ClusterRole pair works unchanged on both AKS and GKE.
How does this clone get the Postgres password onto the cluster, if not Workload Identity?
By hand, deliberately. Terraform generates the password and stores it in Secret Manager as the source of truth, but nothing auto-syncs it into the cluster the way Azure's CSI driver does — a human runs terraform output -raw postgres_password and passes it to helm upgrade --set-file, which renders it into a plain Kubernetes Secret. Simpler to set up for a short-lived clone; the cost is that a password rotation in Secret Manager wouldn't reach the cluster until someone re-runs that command.
Why was container.admin granted and then immediately revoked, twice?
Two one-time cluster setup steps — installing ingress-nginx, and this console's own operations RBAC — needed to create ClusterRoles/ClusterRoleBindings, which the CI identity's standing container.developer role deliberately excludes (so a compromised CI credential can't self-elevate). Each time, container.admin was granted immediately before the one helm command that needed it, from a separate account with IAM-admin rights (the CI identity cannot grant itself roles), and removed immediately after — verified by confirming the CI identity's own getIamPolicy call is rejected again.
What is Terraform state?
A JSON file recording which real cloud resource ID corresponds to each resource block in the .tf files — how terraform plan tells "doesn't exist yet" apart from "exists and unchanged." Without accurate state Terraform can't tell the difference and may try to recreate something already there, which is exactly what happened here when a crashed apply left the GKE cluster running in GCP but absent from state.
Why does this clone use local Terraform state instead of remote, unlike Azure?
Remote state (an Azure Storage Account, in the original) exists so multiple operators can't corrupt shared state and so concurrent apply runs get locked out of each other. This GCP clone is a single-operator, throwaway experiment, so a local terraform.tfstate file is an accepted simplification — at the cost of having no locking at all, which is part of why a crashed apply here could leave state and reality silently out of sync.
How do you troubleshoot CrashLoopBackOff?
kubectl logs <pod> --previous to read the last crash's output, then kubectl describe pod for the Events section, which usually names the exact reason: probe failure, OOMKilled, non-zero exit code, or missing config.
How are DEV, TEST and PROD separated?
Three separate Helm releases of the same chart (migration-app-dev, migration-app-test, migration-app-prod) in three separate namespaces, driven by three separate values files. Only values-prod.yaml carries the full production configuration — Key Vault, ingress, operations-console settings, the correct port and probes.
What happens during a rolling update?
The Deployment creates a new ReplicaSet with the updated Pod template. With maxUnavailable: 0 and maxSurge: 1, Kubernetes starts one extra new Pod, waits for it to pass readinessProbe, then terminates one old Pod, repeating until every Pod is on the new template. Total replica count never drops below desired during the process.
Why do we use readiness and liveness probes?
They answer different questions. Readiness: "can this Pod serve traffic right now?" — failing it pulls the Pod out of Endpoints, no restart. Liveness: "is this process still functioning?" — failing it kills and restarts the Pod. Making liveness depend on the database, for example, would turn an unrelated outage into a full restart loop instead of just marking Pods not-ready.
What is the role of Artifact Registry?
The private registry both application images are pushed to and pulled from — the direct GCP equivalent of ACR. GKE nodes authenticate to it with the default compute service account (granted artifactregistry.reader), so no registry credentials are stored in Kubernetes Secrets or CI variables for pulling images.
How does Ingress route traffic?
The NGINX Ingress Controller watches Ingress objects and configures itself accordingly. Here, path / routes to the console's Service and /pong(/|$)(.*) (rewritten to strip the prefix) routes to Pong's Service — both on the same controller and public IP, distinguished purely by path since neither Ingress sets a host. On this clone that public IP comes from a GCP L4 Load Balancer instead of Azure's Standard Load Balancer, but the Kubernetes-level mechanism is identical.
Why does PostgreSQL need persistent storage?
A StatefulSet Pod can be deleted and rescheduled onto a different node at any time — without a PVC backing its data directory, a Postgres restart would come up as a brand-new, empty database. The PVC (backed by a GCP Persistent Disk here, an Azure Disk on the original) is what makes the data survive the Pod, not just the container.
